# Security boundaries

v4.22 keeps the earlier protections below and the official Discord/profile/network flow; the additional scope of this version is the verified personal package copy for Windows startup. Passing automated checks does not prove that the software has no vulnerabilities or that it will work under every Discord/network condition. Testing with a real account, voice/streaming and a Windows restart is separate verification.

## Protected technical boundaries

- The local proxy rejects plain HTTP `Upgrade` requests without adding the engine credentials. The existing CONNECT flow is kept for HTTPS/WSS.
- Before automatic startup, the owner and the effective write/delete permissions of the EXE and its parent folders are verified. No persistent startup entry is created for a target that other standard users can modify; user permissions are not changed.
- A package in an insecure location is copied, only on a normal manual launch, to a personal location keyed by content hash under the verified user folder. Every parent folder and the target EXE are verified; the pinned engine hash, read-only source handles and the target files' own permission/content checks are kept. Existing files/ACLs are not changed; conflicting or partially written files are refused. The restart does not use a shell and keeps the existing single-session lock. Automatic startup, restore, console mode and the Discord-opening action do not create an installation.
- The single-session lock and the Discord open/status/startup signals are kept in private Windows object namespaces bounded by the user SID. A matching visible name created in advance by another user does not count as a trusted session. A per-user, single-writer file lock also prevents a second connection across processes holding on to an old namespace and across different Windows sessions. Each primary process creates its own namespace with a new GUID and holds it for its lifetime. The discovery record contains only the version, user SID, Windows session and GUID; at most 512 bytes are read from a verified file handle. On shutdown, the record is cleaned up while the same lock is still held. A requesting process opens only a verified existing namespace; it does not create a file or namespace or take lock ownership. `--restore` does not set up a signal listener.
- Temporary executable download support and installation recovery records are verified against the opened file's own owner and effective modification permissions. A trusted parent folder alone is not considered sufficient. Permissions are checked again after a file replacement; verified executable support is protected by a read-only file handle for the whole session. While a pending restore record is kept, shutdown releases the file handle.
- File replacement backs up the file that was actually displaced and compares it with the expected content. On conflict, unknown data is preserved. Deletion is performed through the handle of the verified open file.
- The engine is rebuilt from stable sing-box 1.14.3 sources, pinned dependencies and hash-verified HTTP source changes. The source archive, toolchain, dependency locks, source changes and resulting EXE hash are verified. The license inventory is based on the Go build information of the distributed EXE.
- The engine's HTTP listener accepts at most 128 pending unauthenticated connections without creating parser goroutines. Authentication has an absolute limit of 5 seconds per connection and 64 KiB for each request line plus headers. Repeated failed authentication attempts do not extend the deadline. After successful authentication, read/write deadlines are cleared and capacity is released; file bodies and CONNECT/WSS tunnels are not subject to these size/time limits. Authentication is checked again on every HTTP request.

## Scope

The program runs with standard user privileges. The local proxy is open only to verified Discord processes and the app's own operations. No global Windows proxy/DNS/routing setting, driver, TUN or system service is installed. Downloaded files are not run automatically. The official Discord EXE and the existing profile are used; the shortcut target is kept.

No separate security boundary is claimed against malware that has taken over the same user's privileges or against an administrator/SYSTEM attacker. File operations do not provide an absolute compare-and-swap guarantee in the Windows file namespace; conflict backups exist to preserve user content. If user permissions are changed independently after the package entry is set up, a past check cannot secure the next Windows startup.

This project is unsigned. An open-source license, hash checks and passing tests do not provide Smart App Control or anti-cheat approval. Security policies are not lowered; blocked local tests are not run by a different loading method. GitHub Actions has been removed; Windows regressions are run manually in an approved development environment. Past automated test records do not count as verification of code that changed afterward.

The vulnerability reporting path and the supported version policy are in [SECURITY.md](../SECURITY.md). In regular bug reports, do not share account tokens, profiles, signed attachment URLs, the recovery journal or `.preserved` files. The program version, a short error code and reproduction steps stripped of personal data are enough.
